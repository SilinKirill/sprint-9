# Задание 2. Разработка сервиса отчётов

После добавления Task3 общий стенд запускается по [инструкции Task3](../Task3/README.md); `/reports` теперь возвращает ссылку на сохранённый JSON. Ниже описана подготовка данных Task2.

Сервис предоставляет пользователю отчёт о работе его протезов. Данные подготавливаются по расписанию и доступны через отдельный API и существующий интерфейс приложения.

## 1. Архитектурное решение

[architecture.drawio](architecture.drawio) содержит доработанную C4 из Task1. К существующим компонентам добавлены Apache Airflow, витрина ClickHouse и отдельный сервис отчётов. Исходная база данных обозначена как «Телеметрия DB» и используется вместе с CRM как источник для подготовки отчётности.

Поток подготовки и получения отчёта: **CRM и телеметрия → Airflow → ClickHouse → API /reports → bionicpro-auth (BFF) → UI**. Airflow объединяет данные и рассчитывает показатели, API предоставляет готовый отчёт, BFF связывает запрос с авторизованным пользователем.

## 2. Airflow DAG и витрина

Код Airflow вынесен в отдельную папку [airflow/](airflow/). DAG [bionicpro_daily_reports](airflow/dags/report_etl.py) написан на Python и запускается ежедневно в **00:00 UTC (03:00 МСК)**. Каждый запуск обрабатывает предыдущие полные сутки UTC. Предыдущие периоды можно обработать вручную командой backfill.

Источники размещены в PostgreSQL: CRM хранит клиентов и принадлежащие им протезы, база телеметрии — измерения. ETL объединяет их по клиенту и протезу, рассчитывает суточные показатели и загружает результат в таблицу `reports.daily_reports` в ClickHouse. Витрина хранит количество измерений и успешных движений, среднее время реакции и минимальный заряд батареи по каждому протезу пользователя.

После полной загрузки Airflow отмечает сутки как готовые. API использует только полностью подготовленные данные; повторная обработка периода не удваивает показатели. Структура источников находится в [sources/init.sql](sources/init.sql), витрины — в [clickhouse/init.sql](clickhouse/init.sql).

## 3. API отчётов

Отдельный сервис [reports-api](reports-api/) реализован на **Java 21 / Spring Boot**. Эндпоинт `GET /reports` обращается к ClickHouse и возвращает JSON с суточными показателями. Объединение CRM и телеметрии и расчёт показателей выполняются заранее в Airflow.

Без параметров возвращается отчёт за последние подготовленные сутки. Для выбора периода используются `from` и `to`, например `/reports?from=2026-10-14&to=2026-10-15`. Обе даты включительны, максимальный период — 31 день.

Перед выдачей отчёта API проверяет готовность каждого дня выбранного периода. Если хотя бы один день ещё не обработан Airflow, пользователь получает сообщение о неготовности периода. Отсутствие измерений в обработанном периоде отражается нулевыми счётчиками и `null` для показателей, которые невозможно рассчитать.

## 4. Доступ к собственному отчёту

Используется авторизация Task1: обычный вход или Яндекс ID с OTP и серверной сессией. Браузер обращается к BFF с сессионной cookie, а BFF передаёт access token внутреннему API отчётов. Токены остаются на сервере.

API проверяет токен и определяет пользователя по его идентификатору `sub`. Этот же идентификатор хранится у клиента в CRM. Запрос к витрине ограничивается данными этого пользователя; выбрать чужого пользователя параметром запроса нельзя. Без действующего входа доступ к отчётам закрыт.

## 5. Получение отчёта из UI

В [ReportPage.tsx](../Task1/frontend/src/components/ReportPage.tsx) добавлены поля выбора периода и кнопка «Скачать отчёт». Вызов `/reports` реализован в [api.ts](../Task1/frontend/src/api.ts) через BFF с существующей сессионной cookie.

Браузер сохраняет полученный отчёт в JSON-файл. Если период ещё не готов или данных о протезах пользователя нет, интерфейс показывает соответствующее сообщение и сохраняет вход пользователя.

## Запуск и проверка

Нужны Docker Desktop с Linux-контейнерами и настроенный Task1 по [его инструкции](../Task1/README.md). Все команды PowerShell выполняются **из корня репозитория в одном окне терминала**.

```powershell
$dc = @('--env-file', 'Task1/.env', '-f', 'Task1/docker-compose.yaml', '-f', 'Task2/docker-compose.yaml')
docker compose @dc up -d --build
```

- Приложение: [https://localhost:8443](https://localhost:8443).
- Airflow: [http://localhost:8081](http://localhost:8081), логин `admin`, пароль `airflow_demo`.

### Подготовка данных

Подготовить тестовые данные за двое предыдущих суток для существующего пользователя `prothetic1` и вручную запустить DAG за этот период:

```powershell
$reportSubject = docker compose @dc exec -T keycloak_db psql -U keycloak_user -d keycloak_db -Atc "select id from user_entity where username='prothetic1' and realm_id=(select id from realm where name='reports-realm')"
if ($LASTEXITCODE -ne 0 -or -not $reportSubject) { throw 'Пользователь не найден' }
docker compose @dc run --rm --build demo-data --subject $reportSubject.Trim()
$firstDay = [DateTime]::UtcNow.AddDays(-2).ToString('yyyy-MM-dd')
$lastDay = [DateTime]::UtcNow.AddDays(-1).ToString('yyyy-MM-dd')
docker compose @dc exec -T airflow-scheduler airflow dags backfill -s $firstDay -e $lastDay --reset-dagruns --yes bionicpro_daily_reports
```

Для проверки используется ручной запуск; последующие ежедневные запуски выполняются по расписанию.

### Проверка через UI

1. Открыть приложение и войти под `prothetic1` / `prothetic123` с OTP.
2. Выбрать даты от `$firstDay` до `$lastDay` и нажать «Скачать отчёт». JSON должен содержать только два протеза этого пользователя. За каждые сутки у каждого протеза: 3 измерения, 2 успешных движения, средняя реакция 90 мс и минимальный заряд 80%.
3. Запросить текущие сутки UTC. Должно появиться сообщение, что период ещё не обработан Airflow. Вход сохраняется.
4. Войти через Яндекс ID под аккаунтом, отсутствующим в CRM, и запросить обработанный период. Должно появиться сообщение об отсутствии данных о его протезах. Вход сохраняется.
5. Выполнить запрос без входа:

```powershell
curl.exe -k -i https://localhost:8443/reports
```

Ожидается ответ `401`.

## Основные файлы

- `architecture.drawio` — архитектура подготовки и получения отчётов.
- `airflow/` — DAG и скрипт наполнения данных для проверки.
- `sources/init.sql`, `clickhouse/init.sql` — таблицы источников и витрины.
- `reports-api/` — отдельный сервис отчётов.
- `docker-compose.yaml` — компоненты отчётности, запускаемые вместе с Task1.
- `../Task1/bionicpro-auth/`, `../Task1/frontend/` — подключение API к авторизации и интерфейсу.
